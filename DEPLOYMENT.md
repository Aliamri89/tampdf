# Deployment — tampdf.com (Hostinger)

Production runbook for this monorepo. Every setting below exists because a
real production failure required it (500/503 errors, wiped uploads, hanging
builds). **Do not remove or "simplify" any of it without reading the reason
first** — each item lists the failure it prevents.

Everything here was verified against the code in this repo. Settings that
live only in Hostinger's hPanel (and therefore cannot be read from the
repo) are marked **hPanel** — confirm those in the panel itself.

---

## 1. Hosting model

| | |
| --- | --- |
| Host | Hostinger Business — **Node.js Web App**, run by **Phusion Passenger** |
| App root (Passenger) | `.../domains/tampdf.com/.builds/current/nodejs` |
| Startup file (Passenger) | `server.js` — **hardcoded**, not user-editable (confirmed with Hostinger support; hPanel exposes no "Startup File" option) |
| Deployment trigger | Git integration — pushing to `main` starts a build automatically. There is no CI workflow in this repo (`.github/` does not exist). |
| Database | External Postgres (Supabase free tier, **Session pooler** connection string — Hostinger's outbound network is IPv4-only, and Supabase's direct connection is IPv6-only) |

Passenger always looks for a plain `server.js` at the root of whatever
directory it treats as the app root — never a nested path. That single
constraint explains the entry-file layout in section 3.

## 2. Build pipeline

Always build from the **repo root**:

```bash
npm run build     # root script — required
```

Root `package.json` → `build`:

1. `npm run build -w web`, which in `apps/web/package.json` runs:
   - `npm run clean` — deletes `.next` (stale output has caused bad builds),
   - `payload run ./scripts/clear-dev-migration-marker.ts` — removes the
     `batch: -1` row Payload's dev-mode schema push leaves behind. Without
     it `payload migrate` shows an interactive "data loss will occur,
     proceed?" prompt that has no non-interactive override, and the build
     hangs on Hostinger (no TTY). It only deletes that bookkeeping marker,
     never content.
   - **`payload migrate`** — applies `apps/web/migrations/*` to the
     production database. **This is how production migrations get applied:
     automatically, at build time, before `next build`.** It must run before
     the build because `next build` prerenders pages that query Payload.
   - `next build`.
2. `cp -r apps/web/.next/static apps/web/.next/standalone/apps/web/.next/static`
3. `cp -r apps/web/public apps/web/.next/standalone/apps/web/public`

> ⚠️ Steps 2–3 are **mandatory**. Next.js's standalone output deliberately
> omits `public/` and `.next/static` (per Next's own docs). Running
> `npm run build -w web` directly (skipping the root script) produces a
> standalone folder with no CSS/JS assets and no `public/` files — the site
> then loads unstyled, and `/pdfjs/*`, favicons, and logos 404.

Whenever a Payload collection/global changes, generate and commit a
migration (`npm run migrate:create -w web`) and regenerate
`payload/payload-types.ts` (`npm run generate:types -w web`) — that file is
intentionally committed because the host can't run the generator.

## 3. Deployment artifact and entry file

`apps/web/next.config.ts` sets **`output: "standalone"`**. The build then
produces a self-contained app at:

```
apps/web/.next/standalone/apps/web/
├── server.js        ← generated by Next.js; this is the entry file
├── package.json
├── node_modules/    ← only the traced dependencies
├── .next/static/    ← copied in by the root build script
└── public/          ← copied in by the root build script
```

(The `apps/web/` nesting comes from `turbopack.root` pinning the workspace
root — Next preserves the path relative to it.)

**hPanel settings**

| Setting | Value |
| --- | --- |
| Output directory | `apps/web/.next/standalone/apps/web` |
| Entry file | `server.js` (the generated one *inside* that directory) |

This is the mismatch that broke production before: pointing Hostinger at the
source tree (or at an entry file that doesn't exist inside the deployed
directory) makes Passenger fail to boot the app, which surfaces as 500s on
every route.

### The three `server.js` files — which is which

| File | Committed? | Module format | Purpose |
| --- | --- | --- | --- |
| `.next/standalone/apps/web/server.js` | No — build output | CJS (generated) | **The production entry file.** Serves the built app with no extra dependencies. |
| `server.js` (repo root) | Yes (`8ee877f`) | CommonJS | Fallback for when Passenger's app root is the built *repo checkout* instead of the standalone folder: Passenger only looks for `server.js` at the app root, and the real app lives in `apps/web/`. Boots `apps/web` through Next's programmatic API. |
| `apps/web/server.js` | Yes (`94a5b4a`) | ESM | Equivalent of `next start` as a runnable file, for hosts that run a single "Entry file" via `node <file>` and can't run an npm script. |

All three are kept on purpose. Deleting the root one breaks the fallback
path that Passenger's hardcoded lookup depends on.

## 4. Port binding

**Never hardcode a port.** Hostinger assigns one per app and passes it in
the environment. All entry points already honour it:

| Entry point | Port | Host |
| --- | --- | --- |
| generated standalone `server.js` | `process.env.PORT` → `3000` | `process.env.HOSTNAME` → `0.0.0.0` |
| root `server.js` | `process.env.PORT` → `3000` | `process.env.HOST` → `0.0.0.0` |
| `apps/web/server.js` | `process.env.PORT` → `3000` | `process.env.HOST` → `0.0.0.0` |
| `npm start` (`next start -p ${PORT:-3000} -H ${HOST:-0.0.0.0}`) | `$PORT` | `$HOST` |

Note the generated standalone server reads **`HOSTNAME`**, while the two
hand-written ones read **`HOST`**. Don't set `PORT` yourself in hPanel.

## 5. Media storage (uploaded images)

Uploaded media **must be stored outside the deployed app directory.**
Hostinger replaces/re-syncs that directory on every deploy — confirmed in
production: `~/nodejs` was re-synced and the uploads folder inside it was
wiped, while the Postgres rows referencing those files survived, leaving
every image URL broken.

`apps/web/payload/collections/Media.ts`:

```ts
const staticDir = process.env.MEDIA_UPLOAD_DIR
  ? path.resolve(process.env.MEDIA_UPLOAD_DIR)
  : path.resolve(dirname, "../../media-uploads");  // local dev fallback
```

**hPanel:** set `MEDIA_UPLOAD_DIR` to a stable absolute path **outside** the
deploy target, e.g. `/home/<user>/media-uploads`. Without it, Payload writes
into `apps/web/media-uploads/` inside the deployed folder, and the next
deploy deletes every uploaded image. The directory must exist and be
writable by the app user; back it up like any other persistent data.

### Known bug — deferred, do not lose track of it

`apps/web/app/icon.tsx` resolves a CMS-uploaded favicon from a **hardcoded**
path and ignores `MEDIA_UPLOAD_DIR`:

```ts
const filePath = path.resolve(dirname, "../media-uploads", favicon.filename);
```

That path only matches the local-dev fallback. In production, where
`MEDIA_UPLOAD_DIR` points outside the deploy directory, the file is never
found, the route's `try/catch` swallows it, and the site silently serves the
bundled default icon (`apps/web/public/favicon-default.png`) instead of the
favicon uploaded in the admin panel. Nothing is logged.

The fix is to resolve the upload directory once (shared helper) and use it in
both `icon.tsx` and `payload/collections/Media.ts`, so the two can't drift
apart again. Keep the silent fallback — that part is intentional. This was
deliberately left out of the documentation pass; it is a code change and
needs its own verification.

## 6. Environment variables (hPanel → environment variables)

| Variable | Required | Notes |
| --- | --- | --- |
| `PAYLOAD_SECRET` | **Yes** | Signs Payload auth tokens. App refuses to start without it. Unique per environment. |
| `DATABASE_URI` | **Yes** | Postgres. Use Supabase's **Session pooler** string (IPv4). Percent-encode special characters in the password. |
| `MEDIA_UPLOAD_DIR` | **Yes in production** | Absolute path outside the deploy directory — see section 5. |
| `SERVER_URL` | Optional | e.g. `https://tampdf.com`. Enables Payload's CSRF origin allowlist. |
| `PORT` / `HOST` / `HOSTNAME` | No | Provided by the host. Don't set manually. |

No `NEXT_PUBLIC_*` variables exist — the public site URL is a compile-time
constant in `packages/config/src/index.ts`.

## 7. Production-hardening settings that must not be removed

| Setting | Where | Failure it prevents |
| --- | --- | --- |
| `output: "standalone"` | `next.config.ts` | Hostinger copies an output directory and runs an entry file from inside it; it never runs `next start` against the source tree. |
| `outputFileTracingIncludes: { "/**": ["./node_modules/@img/**/*", "./node_modules/sharp/**/*"] }` | `next.config.ts` | Runtime `ERR_DLOPEN_FAILED: libvips-cpp.so.*` — file tracing can't see sharp's native binary, so it was missing from the standalone output even though the build succeeded. |
| `experimental.cpus: 1` | `next.config.ts` | Each static-generation worker opens its own DB pool; at Next's default worker count a build peaked at exactly Supabase's 15-connection pooler cap, leaving no headroom for the live site. |
| `turbopack.root` pinned to the repo root | `next.config.ts` | A stale second `package-lock.json` above the checkout made Turbopack infer the wrong workspace root and misplace build output. Also fixes the `apps/web/` nesting inside the standalone folder. |
| Postgres pool caps (`max`, `idleTimeoutMillis: 10_000`, acquisition timeout) | `payload.config.ts` | Connections accumulating at the Session pooler across builds/deploys until it refuses new ones. |
| `clear-dev-migration-marker.ts` before `payload migrate` | `apps/web/package.json` | Build hanging forever on an interactive migration prompt with no TTY. |
| Post-build copy of `public/` and `.next/static` | root `package.json` | Unstyled site and 404s for all static assets. |
| Admin at `/amriadmin` + `X-Robots-Tag: noindex` | `next.config.ts` | Admin panel being indexed. |

## 8. Temporary code currently in the tree

`apps/web/payload/lib/temp-media-error-logger.ts` (wired into `Media`'s
`hooks.afterError`) writes upload failures to `apps/web/logs/runtime-errors.log`,
because Hostinger's Business tier exposes no stdout/stderr for the running
process. It only observes — it never changes Payload's response. Removal
steps are documented at the top of that file; remove it once the
`POST /api/media` 503 is root-caused.

## 9. Troubleshooting a deployment

Start here, in this order:

1. **Deployment type in hPanel** — Node.js Web App; is it pointed at the
   standalone output directory (section 3)?
2. **Entry file** — does `server.js` actually exist inside the configured
   output directory? (If the output directory is the repo checkout instead,
   the committed root `server.js` is the one that must be there.)
3. **`server.js` correctness** — see the table in section 3; check the file
   is the one intended for that directory layout.
4. **Environment variables** — `PORT` never hardcoded (section 4);
   `MEDIA_UPLOAD_DIR` set to an external path (section 5); `PAYLOAD_SECRET`
   and `DATABASE_URI` present.

Then, symptom-specific:

| Symptom | Likely cause |
| --- | --- |
| 500 on every route | App failed to boot: wrong entry file/output directory, or a missing required env var. |
| Site loads unstyled, `/pdfjs/*` and images 404 | The post-build copy step didn't run (someone built with `npm run build -w web`). |
| Images broken after a deploy, admin still lists them | `MEDIA_UPLOAD_DIR` unset or pointing inside the deploy directory. |
| `ERR_DLOPEN_FAILED` / libvips | `outputFileTracingIncludes` removed. |
| Build hangs with no output | Interactive `payload migrate` prompt — the marker-clearing step was skipped. |
| Build fails on `relation "..." does not exist` | A Payload schema change was committed without its migration. |
| Intermittent DB connection errors during a build | Pooler connection cap — check `experimental.cpus` and the pool settings. |

## 10. Verifying a deploy

After a build finishes, check from outside:

```bash
curl -o /dev/null -s -w "%{http_code}\n" https://tampdf.com/ar
curl -s https://tampdf.com/sitemap.xml | grep -c "<loc>"
```

- Homepage and a few tool pages return `200` (a wrong entry file gives 500s
  on everything).
- Static assets resolve, e.g. `/pdfjs/cmaps/78-EUC-H.bcmap` and a chunk from
  `/_next/static/chunks/…` return `200`. (Note `Identity-H.bcmap` and
  `FoxitSans.pfb` do **not** exist in pdfjs-dist v6 — don't use them as
  probes.)
- Run one client-side tool in a browser and confirm
  `POST /api/tool-usage-events` returns `201`. That single request proves
  the app booted, the database is reachable, and the latest migration
  (tool-slug enums) was applied. It also records one row in the admin usage
  stats, so use a recognisable test file name.
- `/amriadmin` returns `200`.
- Uploaded images from before the deploy still render (media persistence).
